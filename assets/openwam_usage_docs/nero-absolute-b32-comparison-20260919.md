# 本地四卡绝对 EEF：B32 与 B64 对照

2026-09-19，在用户已批准的 GPU 3、4、5、6 上，以相同 base、reader、精度、冻结策略和性能优化进行对照。
两组均为梯度累积 1，各完成 24 次真实优化器更新，统计第 5–24 步最慢 rank 的整步墙钟。
B32 通过 CLI 临时覆盖，未改正式 YAML 或启动正式训练。结果提交审核后，用户选择“暂不启动，保留当前配置”；正式配置继续保持 B64/GAS1。

| 指标 | B64/GAS1 | B32/GAS1 |
|---|---:|---:|
| 全局 batch | 256 | 128 |
| 稳定整步均值 | 19.552 秒 | **5.628 秒** |
| 稳定步时范围 | 19.519–19.689 秒 | 5.566–5.755 秒 |
| 样本吞吐 | 13.09 窗口/秒 | **22.74 窗口/秒** |
| 5 遍优化器更新数 | 16045 | 32085 |
| 5 遍纯计算估算 | 87.14 小时 | **50.16 小时** |
| 每卡训练进程显存峰值 | 75.10 GiB | **65.37 GiB** |
| PyTorch allocated 峰值 | 69.48 GiB | 56.28 GiB |
| PyTorch reserved 峰值 | 73.87 GiB | 63.75 GiB |
| 每 rank 分配重试总数 | 24（第 2 步发生，此后不增长） | **0** |

按窗口吞吐而非仅按 step 比较，B32 提高约 **73.7%**；相同 5 遍数据的纯计算估算降低约 **42.4%**。
总时长估算未包括初始化、保存、外部作业竞争及长时波动；B32 的保存次数更多，不能把 50.16 小时当作完整 wall time 的保证。

## B32 分段与运行状态

rank0 CUDA event 均值：T5 缓存 0.00139 秒，图像预处理 0.16175 秒，VAE **1.23838 秒**，前向/loss 0.95251 秒，反向 3.04826 秒，DeepSpeed 更新 0.20510 秒。
分段 event 和整步墙钟定义不同，不要求精确求和。VAE 没有出现 B64 的持续 11 秒级退化。
四卡 GPU 利用率均值约 97.1%–99.1%，训练进程树 CPU 均值约 6.74 个逻辑核。
每个 rank T5 只编码一次，三条任务文本缓存正常；所有 step 的 loss、grad norm 和 LR 有限，四个 rank 均完成 24 步，退出码 0。

初次 B32 诊断在真正训练前被诊断脚本的错误步数断言拦住（误写 3217，应为 6417），已仅修正诊断脚本后重跑。
该错误不属于 reader/trainer 或 B32 显存故障；原始失败日志另行保留，表中均为重跑成功结果。

## 对训练方案的影响

- 保持 5 epochs，使用 821344 个完整窗口：B32 每遍 6417 步，尾部补齐 32 个窗口，共 32085 步。
- 仍采用 LR 1e-4、cosine、warmup5%，warmup 自动为 1604 步。没有自动增加梯度累积，也没有按卡数切换训练策略。
- 动作、状态、相机、归一化、损失定义和数据覆盖规则都不变，但 batch 更小、更新次数更多，不能保证最终权重或任务效果与 B64 一致。
- 若仍每 2000 步保存、4000 步独立归档，这些保存点对应的样本覆盖量约为原 B64 的一半；保持的是步数间隔。
- 不能把 B32 的 max_steps 强制保留为 16045 同时又宣称覆盖 5 遍；那只有约 2.5 遍。

性能上建议采用 B32/GAS1；用户本次选择暂不启动、保留当前配置，因此未修改 batch 或 run name，也未创建正式训练 tmux 会话。
